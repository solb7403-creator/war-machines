## Reproduced serious failures and contained changes

1. **P1: duplicate Stars callbacks inflated revenue.** Baseline delivered the same 1,000-Star charge twice: inventory stayed 1,050 Gold, but `meta/revc` became 2,600 cents instead of 1,300. The old unconditional `revAdd` ran after the inventory duplicate guard. Revenue and a durable event marker now commit together through Firebase conditional writes. Prices, 1.3 cents/Star valuation and 25% LP share are unchanged.
2. **P1: delayed Stars replay granted twice.** Baseline replay after 12 later purchases raised Gold from 13,650 to 14,700 because `S.gout` was bounded to 12 entries. New permanent `S.starReceipts[charge]` is part of the same economy CAS as the grant. Existing `starsPaid` receipts are recognized during upgrade; old recorded sales are not added again.
3. **P1: success replay erased refund status.** Baseline overwrote `starsPaid/.../rf`; a later duplicate refund deducted revenue again despite the inventory refund guard. Refund state is now permanent in the economy receipt; conditional receipt projections preserve terminal refund flags. New success/refund accounting retries recover after failed writes. Refund-before-success is recorded as a tombstone and later success grants nothing, with net-zero revenue.
4. **P1: SOL pricing failed open and proof lacked buyer/order binding.** With the local price endpoint unavailable, `amt:0`, a caller-selected memo and a historical fixture transaction with zero recipient credit were accepted and granted 1,050 Gold. Healthy prices rejected the amount. Existing server verification never checked a reference or memo belonging to a server-issued order. Smallest safe containment pauses SOL in backend, primary game UI and standalone `pay.html` direct-link checkout; rate validation also fails closed. No reference-validation claim is made.
5. **P1: account linking changed the owner of replayed Stars charges.** Reproduced the same charge granting another 1,050 Gold to a newly canonical Lunar account; its refund then left the original Telegram account holding the item. An immutable `starsChargeOwner/<charge>` claim now pins both success and refund handling to the original economy owner. Initial claims recognize legacy `tg_<id>` receipts after linking. Independent review reproduced a later broken/orphan link blocking a known refund; pinned owner lookup now happens before mapping resolution, validates the original Telegram user, and remains refundable despite the broken link.
6. **Settlement recovery gap corrected during implementation:** a TON receipt marked granted before revenue failure made the next callback return early without recovering revenue. TON now freezes cents/event ID in the durable economy receipt and payment projection. Retry restores the projection/accounting without another grant. Historical receipts without the new accounting marker retain their existing totals.

## State handling and remaining certification gates

- **Quotes/confirmation:** Stars invoice price is calculated from server state, with `XTR`, buyer ID and nonce in the provider payload. Precheckout checks currency and payload buyer only; it does not persist/consume a server quote or recheck current price, offer use or ownership. Multiple stale invoice/offer and season-boundary scenarios need explicit product semantics and provider tests. TON uses client-side displayed price and memo; the server compares current rules at settlement, without a persisted quoted-price expiry. Race/price-change behavior across concurrent orders is not certified.
- **Idempotency/replay:** local tests cover immediate/concurrent/delayed Stars success replay, repeated/concurrent refunds, refund-before-success, legacy receipt replay, and failed accounting writes followed by retries. TON signature/hash ownership claims and durable receipt retry behavior are implemented. A global immutable charge-owner claim prevents canonical remapping from regranting the same charge or reversing a different account; the fixture verifies both new and pre-upgrade Telegram receipts.
- **Pending/failure/cancel:** Stars grants only from webhook in server economy; `starsDeliver` polls, boot recovery shows unacknowledged receipts up to 30 days old in batches of ten. The client handles paid/failed/cancelled callbacks; explicit `pending` invoice UI is absent. TON wallet response is queued for server verification; server returns `pending` when chain lookup has no match. Queue resumes for 48 hours; client TON pending discovery expires after two hours and examines the latest 50 recipient transactions. Delayed/busy-provider delivery outside these limits needs support or reconciliation. Cancellation does not grant.
- **Refunds:** Stars reversal consumes the exact recorded outputs through shared `ecoRefund`, adjusts verified spending and flagging, and refreshes the effective loadout. The audit verifies callback handling, not actual Telegram refund issuance. Spent duplicate-compensation points/shards and already-claimed pass rewards follow existing clamp/reversal rules, rather than creating debt; no balance/reward policy was changed. TON/SOL refunds remain a manual support policy without a server refund reconciliation implementation.
- **Provider proof limits:** TON feed matching does not explicitly inspect transaction success/finality fields beyond memo/value/hash. SOL historically checked confirmed recipient net balance only; no source ownership, server order, reference or age binding. SOL must stay paused until that is resolved.
- **Operational/accounting limits:** accounting is retry-recoverable, not a background reconciliation service. If a provider never retries a failed webhook, settlement remains pending. The durable per-account receipts and global `meta.paymentEvents` journal grow with purchases; throughput/storage compaction needs a design that retains permanent replay protection. Existing pre-upgrade aggregate revenue cannot be reconstructed from these fixes and was intentionally left unchanged. TON's existing unavailable-price fallback to bounded client USD is preserved and remains a valuation-certification gap.
- **Standalone SOL page:** after parent authorization, `pay.html` now replaces checkout with an unavailable message and returns before wallet detection, QR, copy or send code. A minimal DOM/VM fixture confirms an old/direct link cannot reach wallet code.

No live Telegram invoice, Stars payment/refund, TON wallet transaction, SOL transaction, provider credentials, on-chain finality, production database rules/ETags, Telegram retry SLA or provider outage behavior has been certified. Passing mocks do not establish commercial readiness.
