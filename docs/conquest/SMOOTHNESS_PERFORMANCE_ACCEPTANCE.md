# Conquest flagship — mandatory smoothness and performance acceptance contract

**Purpose:** The owner specifically requires Conquest to feel immensely smooth in the final game. This contract is **mandatory** for both complete flagship briefs and every Codex/Claude continuation. It does not approve reducing content or hiding missing simulation behind visuals; perform end-to-end performance engineering while delivering the whole game.

## Experience standard (test, not merely claim)

- On representative modern iPhone Safari and Telegram Mini App, **target stable 60 FPS** during ordinary exploration, steering, multi-touch FIRE/Dash/Shield, AI engagement, camera orbit, mission combat, physically growing bases and dense raids. The actual full game must be playable and responsive, not only a blank synthetic benchmark. Record measured median/p95 frame times and time spent below 50/40/30 FPS for each scenario. A typical 60 FPS frame budget is 16.7 ms.
- During the **heaviest intended on-screen fight**, still aim for 60 FPS on capable devices through quality adaptation, effects culling and AI batching. On older or thermally limited phones, preserve at least a **stable, responsive 30 FPS** rather than jittering unpredictably; prioritize controls and critical target cues. State actual device constraints rather than claiming all phones can achieve 60.
- Input should react visually on the **next rendered frame** in typical conditions: joystick motion, Dash activation, FIRE muzzle/beam feedback, shield activation, target lock, camera orbit. Input must never wait for a round-trip server acknowledgement. Preserve the server as the authoritative source of hits, economy, ownership and progress. With 50ms server simulation commands and current ~1-second request pumping, implement bounded local prediction and *non-jarring* reconciliation, never client-trusted rewards or fabricated positions.
- No repeated unexplained stalls above **100 ms** under normal tested conditions. Log worst stalls and causes (startup, streaming, terrain, asset upload, server snapshot, burst of enemies). During a densely populated raid, use quality adaptation rather than abandoning the controls or allowing multi-second freezes.
- Memory must remain bounded through at least **30 minutes continuous travel and fighting** plus a **20-minute dense raid** on actual mobile-class hardware. Avoid monotonically increasing geometry, shader/material, projectile, effect, audio or texture allocations. Monitor GPU draw calls, JS heap and renderer geometry/texture counters. Avoid leaking listeners on return/reopen or WebGL context restoration.
- Loading and travel must **not freeze** when chunking terrain or approaching a base. Preload likely near-field chunks, queue asynchronous low-priority builds, progressively refine far detail, bound active chunks, pool/reuse enemies/projectiles/materials, stagger AI decisions, keep critical weapon/projectile math deterministic.
- Preserve deliberate weapon feel without losing responsiveness. Moonbeam must remain a crisp laser weapon with visually readable normal bolts and a distinct cinematic Super, using mobile-safe shader/material/effect pooling. Heavy VFX must degrade gracefully rather than blank the display or produce a huge opaque circle.
- Quality settings must be device-adaptive with explicit HIGH/LOW/2D fallback. Reasonable defaults on iPhone; automatic pixel-ratio, shadow/fog/particle/beam detail and view-distance adjustments based on sustained measured load, with hysteresis so quality does not visibly flicker. Do not change gameplay hitboxes, enemy AI outcomes, weapon reach or reward rules when adapting visuals.
- Maintain responsive accessible mobile HUD. Confirm joystick + FIRE + Dash + Shield work simultaneously through real multi-touch, iPhone safe areas, landscape/portrait, Telegram WebView, resumed app, poor connection and reconnection. Visual effect and aim should originate from the correct cannon muzzle/canonical direction. No ghost input or lost hold when another finger releases.
- Avoid solving framerate by hiding all opponents, making enemy AI idle, or postponing meaningful objectives. Performance test scenes must have representative garrisons, squads, bases, active projectiles, loot effects and on-screen objective cues. Distinguish visually streamed enemies from server-authoritative enemy state; do not spawn fake reward-bearing actors.

## Required implementation practices

1. **Profile first:** Establish a baseline before optimizing; name bottlenecks from existing `ConquestView`, `js/conquest/view.js`, `app.js`, `session.js`, `world.js`, `combat.js` and Worker replay; Graphify may help locate dependencies. No blanket rewrite or engine replacement.
2. **Main-thread discipline:** Bound work per animation frame, particularly world streaming, mesh construction and large UI updates. Precompute/cache terrain and reusable geometry; pool short-lived objects; cap draw calls and texture memory based on actual measured device data. Prefer batching and instancing repeated scenery while preserving distinct mech silhouettes/targets.
3. **Simulation and network:** Deterministic fixed timestep independent of render FPS, accumulated delta handling without runaway catch-up, visible input prediction, robust server-time accounting, accurate authoritative acknowledgement reconciliation. Test 15/30/60 FPS determinism and variable latency/jitter with no duplication of action, loot or banked reward.
4. **Built-in performance proof:** Add a reproducible mobile-density stress route with 2+ combat bases, active patrols, concurrent VFX, a defense event and mission HUD, not just loading terrain. Record scenario, expected active enemy counts and objective logic, actual measured frames/stalls, memory movement, renderer calls and CI evidence. Use Playwright Chromium/WebKit emulation for automated reproducibility, **clearly label this as software/browser evidence**, never claim it proves physical iPhone/Telegram performance.
5. **Real device gate:** When physical devices or live Telegram WebView cannot be exercised autonomously, state `PHYSICAL_IPHONE_NOT_TESTED` and give a minimal owner test path. Never claim the experience is fully smooth on a physical device without actual measurement.
6. **Regression gate:** Preserve existing account/commerce, PvP/Arcade, Conquest survival, earned engineering/gear entitlements, authoritative events, migration and 2D fallback. Capture before/after visuals and performance for identical dense encounters. Tests must cover opening 15 minutes, post-base unlocked encounters, at least one maximal enemy density raid, moving Dash plus FIRE, Moonbeam heat/beam VFX and reload/reconnect.
7. **Release criterion:** Session 1 must already feel smooth and responsive in the active opening combat region; Session 2 must still be smooth after adding all late-game content, including a fully developed physical base and the densest raids. Do not declare completion solely because CI/unit tests pass. If the performance gate genuinely fails, record the blocker and correct it on the current branch before declaring success.

## Proof required in the final handoff

Provide an accessible per-device/per-mode table with scenario, available hardware, observed FPS median/p5 or frame-time median/p95, worst hitch, renderer calls/triangles if available, memory trend, input-to-photon approximation where measurable, reconnect behavior, 2D fallback, and `PASS / CONDITIONAL / FAIL / NOT TESTED`. Notes must distinguish simulation benchmarks from real phone testing. Report exact code SHA and deployed build.

This contract is part of the **complete flagship scope**, not an optional polish pass or separate third planned session. It does not supersede the two full implementation briefs; it raises their acceptance standard.
